# Accounting and End-of-Day Workflows

The Accounting navigation contains General Ledger, Journal Entries, End of Day, and Bank Expense Recording. Reconciliation has its own navigation group; Cash Management retains teller cash-session operations. Pages use the existing MVVM flow: views bind to page ViewModels, ViewModels call typed client services, and services use the shared `ApiClient`.

## Reconciliation

The Reconciliation master page runs unified account/GL and cash checks and displays active exceptions in separate tabs. Row actions are Assign, Perform Reconcile, and Force Pass. Assign opens a dialog for an officer or auditor. Assigned staff use Assigned Reconciliation Tasks, which lists only their work and offers Perform Reconcile. Managers use Reconcile Proposals to accept or reject submitted proposals.

Perform Reconcile opens a case-specific stepper: choose the discrepancy, provide required findings/evidence, then review the suggested amount and correction preview before submitting. Cash and account/GL cases use their corresponding inputs and operational posting workflows. Submitted proposals are immutable and require manager review. Self-approval is allowed only when the proposer is the sole active Manager system-wide and has correction approval permission.

The Reconciliation navigation group also contains Verification. Its Account and GL and Cash tabs list posted corrections whose verification is pending or failed, with the source date, posting date, execution transaction, and last result. Assigned investigators see only their work; correction approvers see all verification tasks. Retry verification runs checks without another financial posting. Passed tasks leave the queue; failed tasks remain with the latest result. This queue includes interrupted verification even if the exception was already marked resolved by a check.

Approval appends linked transactions, accounting records, and GL entries atomically while preserving original entries. Cash-only custody corrections append cash movement records; financial cash corrections also post balanced accounting/GL entries. Verification reruns the relevant check; a passing result clears the exception. Force Pass is an authorized, reasoned decision for the observed source and prevents the exception from reappearing while that source remains unchanged.

Only one open business date is active for ordinary transactions. Starting a new date deactivates the prior date without requiring it to be closed first. Earlier dates remain open for investigation and approved historical corrections. EOD runs the unified check, requires final vault cash validation, then offers date close and the existing force-close request workflow. Summary revisions retain superseded versions for audit.

Bank Expense Recording captures a bank-funded operating expense, payee, purpose, and receipt (or reason no receipt is available). After manager approval, it posts a new expense transaction and balanced Bank Operating Expense/Cash on Hand accounting and GL entries, and records the corresponding cash movement.

## Cash reconciliation

The cash proposal stepper shows a counterpart/retained movement ID for duplicate, transfer and handoff discrepancies, and an accepted handoff ID for handoff corrections. These fields use the shared themed input components. The preview lists the change to every affected cash session. Transfer and handoff verification checks both positions; a missing destination count or remaining mismatch keeps verification failed. Corrected movement amounts are totals, not adjustment deltas. Financial movement errors backed by a valid journal use incorrect-amount/wrong-position operations; custody pair errors use transfer/handoff operations. See the server's `Documentation/CashDiscrepancyCorrections.md` for source requirements.

Session opening and closing/count operations require `cash_operations`; vault opening additionally requires `end_of_day_approval`. The EOD view provides unified exception checks and final vault count; teller session review and operation remain in Cash Management. Cash operators retain the session write controls. Pre-close requires accounting/audit permission, approval/close requires end-of-day approval, and handoff review is available to cash operators, auditors, and EOD approvers.

The cash session date filter defaults to the current server business date, selects an open session automatically when one exists, and can be changed to load another business date's sessions. A new session can only be opened for the active business date. If the selected date is closed or historical, or the server finds conflicting open dates, a modal message asks the user to notify a manager to resolve the business date. Once a session is opened, the list filter returns to the active business date so the new session is visible.

After officer login, the shell checks the current business date for that officer's open teller session and directs officers without one to the Sessions tab. Leaving that page without opening a session shows the themed dialog: “If no opened session, no write can be done.” The session requirement disables and blocks transaction posting and cash-custody operations until an open teller session exists. Account/customer maintenance, reconciliation, EOD workflow actions, and self-service password changes are not teller business operations and remain available according to their own permissions. The shared API client and server enforce the same route scope; opening a teller session remains available.

Cash-session operations use the shared `Input.Text`, `Input.Select`, `Input.Date`, `Card`, and `Tab` theme resources. The session tabs follow the same radio-tab strip used on the Transactions page. Transaction posting and cash-custody buttons visibly disable until the session check confirms an open teller session; session creation stays available.

Cash reconciliation is tab based: Sessions opens and lists positions; Close Session records a physical count and closes that one session; Session History shows movements and count rows. Multiple tellers may each have one open session on the same business date. A nonzero count requires selection of an eligible recipient and creates a pending custody handoff atomically with the count; a zero count needs no recipient. Teller expected cash is server-owned. Cash transactions automatically affect the actor's open teller session; transaction forms do not ask for a session ID. A mismatch creates an exception and never changes expected cash. Inter-session transfers and approved corrections remain server-side operational workflows and are not part of this session-lifecycle screen. EOD's Cash Handoffs tab supports acknowledgement, decline with note, and reassignment. Pending or declined handoffs block business-date close until accepted. NRC pickup branch remains a separate transaction delivery location. The Sessions tab separates the business-date filter and load action from the session-opening controls so they align as distinct operations. The Close Session form uses the full section width, with count and recipient inputs side by side and full-width notes. Session, movement, count, and handoff registers use the shared `Table` DataGrid style and `Card.Flush` / `Card.Caption` components for consistent headers, row states, and spacing.

Opening and count-close commands keep an `Idempotency-Key` across retries and issue a fresh key after success or input changes. Session and handoff mutation commands send the displayed `version`; the server rejects stale edits so the operator can refresh and review the new state.

## End of Day

The EOD workspace uses five themed steps: Run checks, Vault cash, Readiness, Approval, and Close date. Loading a date resumes from persisted run status and the vault's saved count/session state; browsing steps never bypasses server checks. The vault step displays expected cash, the latest actual count and their difference. Recording the final vault count requires all other sessions closed, accepted handoffs, no pending cash funding/receipt or expense requests, and no reserved vault cash. Recording a mismatched count closes the vault session but leaves the cash exception blocking normal EOD. Readiness checks must be rerun after corrections. Manager recheck and approval remain separate actions, followed by an explicit normal Close date action.

Force Close is available in an expandable section on every step for eligible managers. It records a reason and the required manager set, counts the requester as an approver, and automatically closes in the final approval transaction (including sole-manager requests). Closed dates remain selected with their matching run and completion state. A load/refresh resumes pending approvals or completed closure. Remaining exceptions and pending proposals are preserved.

After force close, pending or newly investigated corrections post on the current active open date. Previews and review lists show the posting date alongside the source information. The original exception/session and finalized summaries remain linked to the closed date; no new cash payout occurs from today's session for an already-spent historical amount. A manager must start an active business date before approval can post. Verified current-date corrections provide resolution evidence for historical exceptions.

The `EndOfDayView` is the close workspace: it runs unified account/GL and cash reconciliation, displays exceptions in separate tabs, records final physical vault cash, and provides date close and the manager force-close request form. Starting a new date deactivates the previous one without requiring prior closure; any open date can remain under investigation while the active date proceeds through EOD. Normal close rechecks blockers and generates the GL close audit while holding the business-date lock, then makes the next business date available. Force close bypasses all EOD readiness, reconciliation, unresolved exception, pending proposal, and accounting-integrity blockers after every active user with `end_of_day_approval` at request time has approved. The initiating manager's request counts as their approval; when there is one eligible manager, that approval is sufficient. A reason, the required manager set, each approval identity and timestamp, and the blocker summary are retained on the EOD run. Force close still generates the EOD audit and daily summaries, recording actual accounting differences, and commits the close atomically. It does not resolve exceptions or approve proposals; pending proposals remain pending, and approved financial corrections for the closed source date post on the current active open date. EOD and Exception Center tables use the shared table and caption components. EOD is manually initiated; scheduled financial work and scheduled account reconciliation use the server's existing scheduler.

## Monthly accounting close alerts

The second day of each month at 00:00 Asia/Rangoon runs prior-month account maintenance and interest accumulation before generating `MonthlySummary` rows. If the month's final business date is still open, the scheduler fails with a readable cause after automatic retry attempts are exhausted. Managers with `scheduled_job_management` see the alert in the application header, navigate to the normal End of Day flow to close the date, then retry the same scheduled occurrence. Each request and attempt is retained by the server; the alert clears after a successful retry. Monthly totals use raw accounting entries, while previous-period openings prefer `MonthlySummary`, then later `DailySummary`, and then raw accounting history where no snapshots exist.

### Competing EOD close paths

A pending force-close request does not disable normal checks, review, approval or closure. The EOD view retains the pending force approval separately from the displayed normal run. If normal close succeeds, the request is cancelled and override operations deactivate. If force close succeeds first, unfinished normal runs stop. Reloads show the completed close, and attempted actions from an older page refresh its closed-date state. Financial reconciliation corrections then require a later active open business date; a manager must start it when none exists.

### Reconciliation source selection and manager review

Cash discrepancy inputs use editable, searchable themed selectors rather than manual source-ID fields. A server search narrows account/transaction numbers, movement types or IDs; each category returns at most 500 options. Selected records remain available across successive searches so a source and counterpart can be chosen independently. Movement choices are scoped to the exception's original session and supported discrepancy types; counterpart and destination evidence remain explicit. The form displays the selected original journal and invalidates its preview when source selections change.

Accept and Reject open the full manager review form. It shows original and proposed journal tables, customer before/change/after balances, both cash positions with expected and counted values, findings, evidence, posting date and review notes. The manager makes the final Accept/Reject decision in this form. Cash source changes disable acceptance and display the server warning; rejection remains available. Server approval always revalidates the source snapshot.

The final EOD step exposes persisted audit findings with raw/effective debit and credit, reconciliation status, missing journals, unbalanced raw/combined journals and waiver IDs. Refresh audit findings is read-only. Legacy batches without a stored findings snapshot are identified explicitly.

Visible EOD, reconciliation/assigned-task, proposal and verification views refresh their saved state every ten seconds. The shared Themes.RefreshAssist behavior stops timers on unload and skips hidden views or busy commands. EOD polling never reruns checks or clears in-progress count/reason fields. A completed close by another manager refreshes the selected date and stops obsolete close actions. Active manager review/assignment dialogs hold the parent busy gate so their evidence is not replaced while a decision is being entered. These are bounded polling updates, not push notifications.
